# Fix audit — 2026-08-13 (2.3.5)

**Scope.** A second adversarial audit, run against the **fixes** 2.3.4 shipped
rather than against the code they replaced. Eight lenses (tokenizer bounds,
eval_pow + depth accounting, parse_number, ai.cyr JSON scanning, fuzz-harness
quality, regression-test adequacy, new-defect sweep, gates and docs), each
finding verified by an independent agent instructed to refute it. 74 findings
raised, 39 survived verification.

It found what the first audit could not: that some of 2.3.4's fixes introduced
new defects, and that several of its regression tests and fuzz assertions were
**decorative** — green whether or not the code they guarded was present.

**Toolchain.** Cyrius 6.5.20, x86_64 Linux. Baseline: the released `2.3.4` tag.

## Regressions 2.3.4 introduced

### R-1 — `eval_pow` cap turned `(±Inf)^n` into NaN

`ABACO_POW_EXACT_MAX = 1024` sent every integer exponent above the cap to the
general `exp2(exp · log2|base|)` path. For a base already saturated to ±Inf that
evaluates `exp2(+Inf)`, which returns **NaN**. 2.3.3's linear loop multiplied Inf
by itself and returned ±Inf — the IEEE-754 answer.

```
                          2.3.3      2.3.4      2.3.5
(1e200*1e200)^1024        +Inf       +Inf       +Inf
(1e200*1e200)^1025        +Inf       NaN        +Inf
(1e200*1e200)^2000        +Inf       NaN        +Inf
(0-(1e200*1e200))^2001    -Inf       NaN        -Inf
```

The boundary sat exactly at the cap, pinning the cause. `eval_err` stayed
`ABACO_ERR_NONE`, so it was a silent wrong answer — the class 2.3.4 set out to
eliminate. `test_pow_exponent_cap` used only bases 2, 0.5 and 3, all finite,
which is why it passed.

### R-2 — `0e400` parsed as NaN

`result = f64_from(mant) * _pow10(total)`. `_pow10` saturates to +Inf at k ≥ 309,
and an all-zero significand makes `mant == 0`, so the product was `0.0 * +Inf` =
NaN. Threshold exactly `total ≥ 309`. Affected `0e309`..`0e400`, `00e400`,
`0.0e400`, `.e400`, `0e9999999999`. 2.3.3 returned 0.0 because its exponent clamp
kept the factor finite. A differential fuzz of 4504 random numeric strings
produced 70 NaNs under 2.3.4 and none under 2.3.3.

**Both fixed**, with `test_pow_nonfinite_and_parity` and
`test_zero_mantissa_and_range` pinning them.

## The fix for R-1 and P-1: binary exponentiation

Rather than tune the cap, `eval_pow` now uses square-and-multiply — O(log|exp|),
at most 63 multiplications for any i64 exponent. That resolves three findings at
once:

- **No DoS**, without a cap: `2^1000000000000000000` is ~60 multiplications.
- **No accuracy cliff** (P-1). The cap's "behaviour-preserving" claim was false:
  `0.5^1024` is 2⁻¹⁰²⁴, a normal value that only reaches 0 at exponent 1075, and
  the whole band `0.5004 < |base| < 1.998` is still changing well past 1024
  (`1.001^1024` = 2.7828855, `1.001^1025` = 2.7856684). Handing that tail to
  exp2/log2 cost up to ~493 ulps in a function whose stated purpose is exactness.
- **No non-finite hole** (R-1): squaring propagates Inf and 0 as IEEE requires.

## parse_number corrections

### P-2 — the exponents were still clamped separately

The 2.3.4 comment promised "combine, THEN clamp", but `exp_val` was still
saturated at 400 per digit *before* the combination — so the cancellation bug the
comment described survived verbatim. A literal whose written exponent exceeds 400
while its own decimal exponent pulls the magnitude back into range came out
wrong. The per-digit saturation is now `ABACO_DEC_EXP_MAX` (10⁹), far above the
f64 range, leaving `total = dec_exp + sci` as the only place magnitude is clamped.

### P-3 — the lower clamp broke genuine subnormals

`ABACO_POW10_MAX = 340` was justified as "10⁻³²⁴ is below the smallest subnormal,
so nothing representable survives" — true only for `mant == 1`. The mantissa
carries up to ~10¹⁸, so `mant · 10⁻³⁴⁰` lands around 10⁻³²², inside the subnormal
range. A scan of 710 literals found 296 wrong: 293 returned nonzero where the
answer is exactly 0.0. The lower bound now carries `ABACO_MANT_DIGITS` of headroom.

### P-4 — `_pow10` accuracy — **partially fixed**

Building 10^k by k successive multiplications accumulated enough error to push
the canonical DBL_MAX literal over the top and return +Inf. `_pow10` now splits
the work through the exact 10²² block, cutting the multiplication count from k to
ceil(k/22).

Measured against the correctly-rounded reference:

| literal | 2.3.5 | correct | error |
|---------|-------|---------|-------|
| `1e307` | 9199863512903218226 | …227 | 1 ulp |
| `1e308` | 9214871658872686753 | …752 | 1 ulp |
| `1.7e308` | 9218378953502702453 | …454 | 1 ulp |
| `1.79769313486231e308` | 9218868437227405284 | …282 | 2 ulp |
| `1.797693134862315e308` | 9218868437227405310 | …307 | 3 ulp |
| `1.7976931348623157e308` | **+Inf** | 9218868437227405311 | **saturates** |

**Residual, deliberately left open.** At the very top of the range 1 ulp of
upward error *is* +Inf, so literals within ~2 ulp of DBL_MAX still saturate.
Closing it needs a two-term (double-double) scale factor, which is a
disproportionate amount of new arithmetic for a patch release. Pinned by
`test_top_of_range_literals` so it cannot silently widen, and tracked in
[`../development/roadmap.md`](../development/roadmap.md).

For context on proportion: over a 1510-literal random corpus the mean absolute
error is **1.6 ulp** at 2.3.4/2.3.5 versus **72932 ulp** at 2.3.3. The
mantissa/exponent rewrite is a large accuracy win with one saturating edge.

## ai.cyr — the H-4 fix was incomplete

### A-1 — `_jf_get_object` was never made string-aware

The 2.3.4 fix rewrote `CalcHistory_from_json` and `_jf_find_value` and its own
comment claimed "every structural scan in this module goes through this" —
but `_jf_get_object` still counted raw braces. A `}` inside a rates **key** ended
extraction early, and because `_ccy_load_body`'s only completeness check is
`kept == 0`, a truncated object that still yielded one valid pair was reported as
**success** with a silently incomplete rate table. Same defect class as H-4, in
the module's only network-facing parser. Fixed; `test_ccy_brace_in_key` pins it.

### A-2 — the depth guard could FALSE ACCEPT

`_ccy_json_depth_ok` counted braces and brackets with no floor, so unbalanced
**closers** drove the counter negative and masked genuine nesting from `maxd`: a
key padded with N `]` bytes bought N free levels. That is a false accept — the
one direction a DoS guard must never fail — and it contradicted the function's own
"only ever rejects more aggressively" comment. Fixed with a one-line clamp;
`test_ccy_depth_guard_clamp` and a `fuzz_ai` probe pin it.

### A-3 — 1-byte out-of-bounds write

`CalcHistory_load_from_file` did `alloc(65536)`, `file_read_all(…, 65536)`,
`store8(buf + n, 0)`. `file_read_all` returns exactly `maxlen` for any file at or
above the cap, so the terminator landed one byte past the allocation — precisely
the address the header-less bump allocator would hand out next, and unmapped
memory when the block ended on a chunk boundary. The parser's `strlen` then
depended on a terminator stored outside its own buffer. Now allocates `cap + 1`
and rejects a file at or above the cap rather than silently truncating it.

## Tests and harnesses that did not test

This is the part worth recording. Six separate assertions were green regardless
of whether the code they guarded existed.

### T-1 — the H-3 depth test was decorative

It used 5000 unary minuses (5001 tokens) and a 300-operator `^` chain (601
tokens). **Both exceed `ABACO_MAX_TOKENS`**, so `tokenize` rejected them before
the parser was entered — the assertions were satisfied by H-1's token cap, not
H-3's depth accounting. Verified by reverting the depth fix: the suite stayed
green.

Rewritten to sit inside the token budget (256 accepted, 257 and 300 rejected),
and every rejection now also asserts `eval_ntoks != 0` so a token-cap rejection
cannot masquerade as a depth-cap one. **Confirmed discriminating**: reverting the
`parse_unary` accounting now fails 2 assertions.

A structural note the audit established: `parse_power`'s depth guard is
**unreachable** through `^` chains at `ABACO_MAX_TOKENS = 512` — reaching depth
256 needs ≥256 operators at 2 tokens each = ≥513 tokens. It is retained as
defence-in-depth against a future cap change, and the test now says so explicitly
rather than pretending to exercise it.

### T-2 — the key-confusion test could not fail

Its payload **escaped** the lookalike, so the pre-fix matcher never matched it
either; the test passed identically before and after. Replaced with an unescaped
value that is exactly a key name, with the genuine key after it. **Confirmed
discriminating**: the 2.3.3 parser returns `HIJACK`, 2.3.5 returns `REAL`.

### F-1 — `fuzz_eval` did not detect H-1

The corpus crossed the token boundary but nothing observed the crossing — results
and `eval_err` were both discarded. With every `ABACO_MAX_TOKENS` bound deleted it
passed 50,000 iterations, because H-1's failure mode is a silently wrong answer,
not a crash. Every pathological shape now asserts its contract; the sum shape
checks the value is **exactly** n. **Confirmed**: with the bounds removed it now
fails immediately.

### F-2 — the CRLF invariant was vacuous

The harness advertised "`_ccy_validate_url` NEVER accepts a URL containing a
control byte". The assertion was `has_ctrl == 1 && ok == 0`, but the generated URL
was random bytes, which the scheme check rejects every time — so `ok` was never 0
and the conjunction could never fire. The URL corpus is now a real accepted prefix
plus fuzz bytes, making acceptance reachable, with a mirrored assertion so the
guard cannot be "fixed" by rejecting everything. **Confirmed**: deleting the
control-byte check now fails the harness.

### F-3, F-4, F-5 — further harness gaps

- The MED-7 rate probe hard-coded the third letter of its probe keys to `A` while
  the generator picked all three at random, inspecting **1 key in 26** (measured
  194 of 4028 accepted rates). It now walks exactly the keys planted.
- The deep-nesting block discarded its result. It could not be made
  discriminating end-to-end — `bayan_json_parse` at 6.5.20 is a flat scanner, so
  a nested payload is rejected by `kept == 0` whether or not the guard runs — so
  the guard's contract is now asserted **directly**, together with the A-2
  false-accept probe. **Confirmed**: both neutering the guard and removing the
  clamp now fail.
- No harness could reach the `totient` domain cap: the generators emit no
  function-call syntax, and a 7-letter name is ~8e-16 per position. A fifth
  pathological shape composes calls from a fixed vocabulary.

### T-3, T-4 — untested halves

`implicit_mul`'s separate overflow bound was never exercised (every `test_token_cap`
input is a plain `1+1+…` with no implicit multiplication); `2pi` terms are the only
shape that reaches it — 128 fit, 129 do not. And no test evaluated the
**expression** `round(…)`, so the evaluator binding the 2.3.4 rename exists to
protect could have been switched back to the ties-to-even builtin with the suite
green.

## X-1 — token cap rejected a valid expression

The cap check ran before the byte was classified, so a pass that emitted no token
still counted: an expression at exactly `ABACO_MAX_TOKENS` followed by whitespace
was a false `ABACO_ERR_PARSE`. The check now sits after whitespace handling.

## Verified sound

- The 2.3.4 `_jf_skip_string` / `_jf_find_value` / `CalcHistory_from_json`
  rewrite is **correct for its own scope** — escape handling, forward progress
  and termination all verified independently.
- `fuzz_ai` genuinely works: it caught H-4 on iteration 1 and H-2 by iteration 33,
  and its loader and NL-parser paths are genuinely reached.
- The tokenizer bound is correct: token index `ABACO_MAX_TOKENS - 1` is the last
  written and stays inside the 8192-byte allocation.
