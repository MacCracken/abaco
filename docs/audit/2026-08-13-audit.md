# Security & correctness audit — 2026-08-13 (2.3.4)

**Scope.** Triggered by the Cyrius 6.4.66 → 6.5.20 toolchain bump. Six parallel
lenses (stdlib API delta, builtin/identifier collisions, parser DoS classes,
lint/quality gates, documentation drift, bundle contract), each finding
adversarially verified by independent agents instructed to refute. 51 findings
raised, 22 survived verification.

**H-4 was not one of them.** It was found afterwards by `fuzz/fuzz_ai.fcyr` —
the harness written to close P-1 — on its first run, through a round-trip
invariant no example-based test had thought to assert. Worth recording: the
audit's own recommendation produced a finding the audit itself missed.

**Toolchain.** Cyrius 6.5.20, x86_64 Linux. Baseline for comparison: the 6.4.66
vendored stdlib and the `2.3.3` tag.

## H-1 — `tokenize()` wrote past the token array

`src/eval.cyr`. `ABACO_MAX_TOKENS = 512` was declared and `tok_alloc()`
allocated `512 * 16 = 8192` bytes against it, but no code ever compared the
token counter to it. `grep -rn MAX_TOKENS src/` returned exactly two hits: the
declaration and the allocation.

The consequence was worse than a crash. `alloc()` is a bump allocator, and
`tokenize` calls `alloc(8)` per numeric literal for the `nend` scratch cell, so
those cells sit immediately after the token array. The token frontier advances
32 bytes per term while `nend` advances 8, meeting at term `8192/24 ≈ 341.3`:

```
343 terms ("1+1+...+1")  ->  342     <-- first wrong answer, no error set
350 terms                ->  342
400 terms                ->  342
200000 terms             ->  342
16,000,000 tokens        ->  SIGSEGV
```

`TOK_IDENT` values are pointers, so a corrupted identifier token was handed to
`streq()` as an attacker-influenced wild read.

**Fixed.** `tokenize` bounds every loop pass; `implicit_mul` bounds its own
output separately (it inserts up to one `*` per token, so it can overflow even
when its input did not). Both return `ABACO_TOK_OVERFLOW`, mapped to
`ABACO_ERR_PARSE` by `Evaluator_eval` and `Evaluator_eval_partial`.
Regression: `test_token_cap` — 256 terms (511 tokens) exact, 257 terms a clean
parse error, 343 terms rejected rather than answering 342.

## H-2 — `eval_pow` unbounded integer-exponent loop

`src/eval.cyr`. The exact-result fast path ran `while (i < exp_i)` with `exp_i`
taken directly from user text and no upper bound.

```
2^1000000000000000000    20 bytes  ->  ~10^18 iterations, ~81 years
2^10000000000            13 bytes  ->  25.7 s   (measured)
2^1000000000             12 bytes  ->  2.56 s   (measured)
```

`2**N` and `pow(2,N)` reach the same path. Measured 2.57 ns/iteration, linear.

Every iteration past 1024 was provably wasted: `2^1023` is finite, `2^1024` is
`+Inf`, and the general `exp2(exp · log2|base|)` path returns bit-identical
`+Inf`. This is the same defect class the Cyrius stdlib fixed in `lib/math.cyr`
at 6.4.69 — and abaco's instance was strictly worse, having no clamp at all
where the stdlib had an unbounded accumulator.

One subtlety: `2^1e10` did *not* hang, but only accidentally. `parse_number`
builds `10^x` via `f64_exp2`, which is inexact, so the round-trip equality test
fails and control falls to the O(1) path. Plain decimal literals accumulate
exactly and hit the fast path every time. The existing exponent clamps at
`eval.cyr:190`/`:201` guard only the scientific-notation field and never
covered this.

**Fixed.** Cap at `ABACO_POW_EXACT_MAX = 1024`; larger exponents fall through to
the O(1) path. Verified behaviour-preserving at the edges: `1^2000 = 1.0`,
`0.5^2000 = 0`, negative-base odd/even parity unchanged.
Regression: `test_pow_exponent_cap`. The three inputs now total **2 ms**.

## H-3 — `ABACO_MAX_DEPTH` did not bound unary or power recursion

`src/eval.cyr`. Depth was charged only when entering a parenthesized group or a
function-call argument list. `parse_unary` recursed into itself once per leading
sign and `parse_power` once per right-associative `^`, neither touching the
counter — so `----…--1` and `2^2^2^…^1` recursed until the native stack was
exhausted. `docs/architecture/002-expression-depth-bound.md` and the 2026-04-14
audit both recorded the bound as covering all parser recursion.

**Fixed.** Both functions now increment/decrement depth around their self-calls
and early-out with `ABACO_ERR_PARSE`, matching `parse_expr`.
Regression: `test_unary_and_power_depth` — 200 minuses accepted (and `= +1`),
5000 rejected; 300-deep `^` chain rejected. Architecture doc corrected.

## M-1 — `totient()` unbounded domain

`src/eval.cyr`. Exposed directly to expression input over ntheory's O(√n)
trial-division loop, while `factorial` (n > 170) and `fibonacci` (n > 92) were
both bounded.

**Fixed.** `ABACO_TOTIENT_MAX = 10^12`, keeping the loop under ~10⁶ iterations
while covering any realistic calculator input. Regression: `test_totient_cap`.

## M-2 — `MAX_TOKENS` collided with the stdlib

`dist/abaco.cyr` exported `var MAX_TOKENS = 512`; `lib/patra.cyr` declares
`enum TokLim { MAX_TOKENS = 128; }`. Duplicate globals are a **warning, not an
error**, so a consumer bundling both could silently receive 128 — a 4×
undersized token array — with only a build warning.

**Fixed.** Parser limits namespaced to `ABACO_MAX_TOKENS` / `ABACO_MAX_DEPTH`,
consistent with the `ABACO_ERR_*` convention adopted at 2.3.3. Re-checked: no
other abaco global or function name collides with any 6.5.20 stdlib symbol.

## M-3 — `parse_number` unguarded i64 accumulators

`src/eval.cyr`. `int_part`, `frac_part` and `frac_div` were i64 accumulators
multiplied by 10 per digit with no overflow guard, so a ~19-digit integer
literal wrapped to a **negative** value and a ~19-digit fraction wrapped
`frac_div` into a nonsense divisor. Both returned silent garbage.

**Fixed.** Replaced with an exact 18-digit mantissa plus a decimal exponent
(`ABACO_MANT_DIGITS` = 18 is the largest count for which `mant * 10 + digit`
cannot overflow i64). Past that, digits only move the exponent, so there is no
wrap point left at any input length.

The mantissa/exponent split also beats the obvious alternative (f64 accumulation
with a shrinking `frac_scale`, as `lib/math.cyr` does) on two counts: it keeps
whole numbers **bit-exact**, which `eval_pow`'s integer fast path depends on,
and it makes fractions one correctly-rounded division (`314/100`) instead of an
accumulation of inexact tenths.

Two follow-on corrections came with it:

- The literal's own decimal exponent and the scientific exponent are now
  combined **before** clamping. Clamping separately would let a long fraction
  and a large positive exponent cancel into the wrong magnitude.
- Negative exponents divide in steps, so representable subnormals (`1e-320`) no
  longer collapse to 0 via an intermediate `+Inf` divisor.

Note a deliberate behaviour change: `1e400` now yields `+Inf` rather than the
old finite `1e308`. That is the correct IEEE-754 overflow result; the old clamp
turned an overflow into a plausible-looking finite number, contradicting its own
comment ("anything larger is +inf / 0 already").

Regression: `test_long_literals`.

## H-4 — `CalcHistory_from_json` lost the entire history on a brace

`src/ai.cyr`. Object boundaries were located by counting raw `{` / `}` without
skipping string contents. Braces inside a JSON string are legal and require no
escaping — and `CalcHistory_to_json` emits them verbatim — so a single `{` or
`}` in any input, result or timestamp shifted the boundary and made the rest of
the array unparseable:

```
push "a}b" and "second"  ->  to_json  ->  from_json  ->  0 entries recovered
```

Silently, with no error. `CalcHistory_save_to_file` → `CalcHistory_load_from_file`
therefore discarded the **whole** history whenever any expression contained a
brace — plausible input for a calculator. A `]` inside a field ended the array
early by the same mechanism.

Related, same root cause: `_jf_find_value` matched a key name **anywhere** in
the object slice, so a value whose text resembled a key could be read as that
field. It stayed benign only because `to_json` always writes the genuine key
first; a hand-written or attacker-supplied file carries no such ordering
guarantee, and `load_from_file` reads untrusted data.

**Fixed.** All structural scanning now goes through `_jf_skip_string`, which
honours backslash escapes, and `_jf_find_value` matches only strings in key
position (followed by `:`). Regressions: `test_history_json_braces`,
`test_history_json_key_confusion`.

**Found by `fuzz/fuzz_ai.fcyr` on its first run**, via the round-trip invariant
`len(from_json(to_json(h))) == len(h)` — the kind of property no example-based
test had thought to assert.

## M-4 — `bench_run` changed semantics at 6.5.19

`lib/bench.cyr` now auto-batches and subtracts a **measured** per-boot timer
floor (1.33 µs on the audit machine) from every sample. Prior numbers included
that overhead. Consequences:

- Benchmark figures are **not comparable across the 6.4.66/6.5.20 boundary**.
  Sub-microsecond rows moved most (`round`: 358 ns → 7 ns) because they were
  mostly clock overhead.
- The stdlib notes the floor is per-boot and non-deterministic, so figures are
  not strictly comparable across reboots either.

The 2.3.4 run is recorded as a **new baseline**; the 3-point CSV trend should
not be read across that boundary.

## P-1 — the fuzz harness could not reach any of the above

`fuzz_eval` capped generated input at 48 bytes — against a 512-token limit, a
10× margin it could never close — and emitted `^` only via the ~0.04%/byte
wild-byte path. `src/ai.cyr` has no harness at all.

**Fixed, both halves.**

`fuzz_eval`: length cap raised to 1200 bytes (> `ABACO_MAX_TOKENS * 2`), `^` and
`!` promoted to first-class biased bytes, and every 4th iteration runs a
targeted adversarial shape: long exponent digit-runs, deep unary-sign chains,
deep `^` chains, and token-array overruns. Confirmed to discriminate — the
extended harness **hangs** against the 2.3.3 evaluator and passes 20,000
iterations against 2.3.4.

`fuzz_ai` (new): covers `nl_parse` on both random bytes and grammar-shaped
phrases, `CalcHistory` ring-buffer bounds and JSON round-trip, `_ccy_load_body`
on adversarial rate payloads and deep nesting, and `_ccy_validate_url`. It
asserts this audit's stated safety properties directly rather than trusting
them: every rate surviving the loader is finite / positive / < 10⁶ (MED-7), and
no URL containing a control byte is ever accepted (§4.1). It found H-4 on its
first run, fails against the 2.3.3 `src/ai.cyr`, and passes 50,000 iterations
against 2.3.4.

## P-2 — CI lint gate matched only `warn ` lines

`.github/workflows/ci.yml` grepped `^\s*warn `, but `cyrlint` prints untracked
deferrals under a `deferral line N:` heading followed by a `0 warnings`
summary. Two untracked deferrals in `src/ai.cyr` therefore rode through 2.3.1,
2.3.2 and 2.3.3, each of which recorded "lint clean". **Fixed**: the gate now
matches both forms.

## P-3 — `cyrius lint <glob>` silently checks one file

`cyrlint`, `cyrfmt` and `cyrdoc` accept a single path and ignore extra
arguments without a diagnostic. `cyrius lint src/*.cyr` — as documented in
`CLAUDE.md`'s Quick Start — checked `src/ai.cyr` alone and reported clean for
the crate. **Fixed** in `CLAUDE.md` and `CONTRIBUTING.md`, which now document
the per-file loop CI already used. Re-checked per file at 2.3.4: all 7 modules
clean.

## Verified non-issues

- **No further reserved-word collisions.** Every abaco top-level definition was
  cross-referenced against the 6.5.20 intrinsic set (extracted both from the
  compiler binary and by finding symbols `lib/*.cyr` calls but never defines).
  `f64_round` was the only collision.
- **The 6.4.69 `f64_parse` hardening is inherited.** `src/ai.cyr`'s
  natural-language and currency-rates parsers route through the stdlib parser
  and pick up its exponent clamp automatically.
- **Bundle contract intact.** `cyrius distlib abaco` reproduces
  `dist/abaco.cyr` byte-for-byte; module order still matches `src/main.cyr`'s
  include order; `main.cyr` still excluded.
- **`f64_round` shadowing was not a 6.5.x regression.** Building the 2.3.3 tree
  against 6.2.11, 6.3.10 and 6.4.66 shows all three already resolved
  `f64_round` to the intrinsic (`round(2.5) = 2`). 6.5.x only made it visible
  by reserving the name. See the 2.3.4 CHANGELOG entry.
